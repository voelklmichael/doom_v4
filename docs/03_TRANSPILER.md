# Phase 3: Transpilation & Code Generation Plan

This phase translates the annotated Typed AST from Phase 2 into target programming languages, starting with Rust and extensible to .NET (C#).

---

## 🦀 Target 1: Rust Transpiler

### 1. Architectural Choices
- **Memory Model** -- **Decided in detail** (not yet implemented -- corpus-wide surgery, needs its own scoped build-out before struct translation starts). Corpus investigation found two genuinely different pointer categories, deliberately treated differently rather than one uniform arena:
  - **Level geometry** (`sector_t`, `line_t`, `side_t`, `vertex_t`, `subsector_t`, `node_t`, `seg_t`): bulk-allocated once per level (`p_setup.c`'s `sectors = Z_Malloc(numsectors*sizeof(sector_t), PU_LEVEL, 0)`, one shot, freed all at once on level teardown), individual elements never resized/added/removed mid-level. A pointer into this array is valid for the whole level's lifetime -- no aliasing hazard, no reuse. Maps to a plain index newtype (`SectorId(u32)`, etc.) into a `Vec<T>`; no generation counter needed.
  - **Dynamic entities** (`mobj_t` plus the 8 other structs in `p_spec.h` that embed `thinker_t {prev, next, function}` as their first field -- `fireflicker_t`, `lightflash_t`, `strobe_t`, `glow_t`, `plat_t`, `vldoor_t`, `ceiling_t`, `floormove_t`; a 9th, `slidedoor_t`, is `#if 0`'d out dead code in the corpus itself, confirmed by direct read rather than assumed while translating these -- not a real thinker subclass at all): created/destroyed continuously during play, all linked into one polymorphic list (`thinkercap`) and dispatched via a hand-rolled C vtable (calling `function` as a function pointer). `p_tick.c`'s `P_RemoveThinker` doesn't free immediately -- it sets a sentinel (`function.acv = (actionf_v)-1`); the actual unlink+free happens lazily on the *next* pass through `P_RunThinkers`, which is behavior-relevant timing (a just-marked object is still walkable that same tic) and needs to be preserved exactly, not "simplified" away. **Decided (revised while implementing)**: a hand-rolled *append-only* arena, no generation counter and no free-list -- an initial "generational slot arena with reuse" design was reconsidered once actually specifying its `remove`/`run` semantics: the C original never reuses a slot *position* at all (each thinker is its own independent `Z_Malloc`, not array-backed), and `P_RunThinkers`' single forward pass means a thinker spawned mid-tick (appended at the true tail, ahead of the traversal cursor) is visited in that *same* tick -- a free-list that reused an earlier, already-visited index for that new thinker would make it invisible for the rest of the pass, silently diverging from the original. Always appending at the true end avoids this, and removes the ABA hazard a generation counter would otherwise be defending against -- a hazard *introduced* by slot reuse, not present in the original at all. Tombstoned (removed) slots stay dead permanently within one level's lifetime (bounded -- a level's total thinker count over a whole playthrough is a few thousand at most); the whole arena is discarded and recreated fresh at each level load, matching the original's own `PU_LEVEL` wipe-everything-at-once semantics exactly. **Implemented**: `transpiler/src/codegen/runtime/arena.rs` (`Arena<T>`, `Handle<T>`). Its `run` uses take-then-put-back per slot (`Option::take` the value out, call the per-item closure with both `&mut T` *and* `&mut Arena<T>`, put it back unless the closure removed that exact handle) specifically to support the common real case of a thinker removing itself (or another handle) mid-tick without hitting Rust's aliasing rules -- distinguished internally from removing an *other*, not-currently-processing handle (which clears immediately, safe since nothing borrows that slot).
  - **Polymorphism**: ten concrete thinker types is a small, closed, finite set (confirmed by corpus scan, not assumed) -- **decided**: a closed `enum Thinker { Mobj(Mobj), Ceiling(Ceiling), ... }` with one `match` replacing the function-pointer call in the tick loop, not `Box<dyn Thinker>` trait objects (avoids per-thinker heap allocation, and a `match` gets exhaustiveness-checking for free on a set that will never actually grow). The *other* function-pointer table in the corpus -- `p_mobj.h`'s `mobjinfo_t`/state-table `action` pointers, ~150 `A_Chase`/`A_FaceTarget`-style functions referenced from `states[]` -- is a separate, easier problem: homogeneous in signature (`fn(mobj)`-shaped, no per-variant payload), so likely just real Rust `fn` pointers stored directly in the state table, no enum needed there.
  - **List fidelity**: **decided** to keep the intrusive doubly-linked-list *shape* (each sector's thing-list, each blockmap cell's thing-list) as index-based prev/next `ThinkerId`/`MobjId` fields rather than swapping to a `Vec`/`HashSet` per sector -- the original's iteration order through these lists is occasionally behavior-visible (collision/interaction resolution order), and the project's validation strategy is tick-for-tick behavioral equivalence, not "morally similar" output, so a container swap that could silently reorder iteration is a real risk, not just a style choice.
  - Self-referential `mobj_t` fields (`target`, `tracer`, `player`, `subsector`) fall out for free once the arena exists -- `Option<MobjId>` / `Option<PlayerId>` / `SubsectorId`.
  - Global game state encapsulation (e.g. `DoomState` struct or safe static modules) -- still open, likely follows from however the arena(s) end up organized.
- **Fixed-Point Arithmetic** -- **Decided and implemented**: `fixed_t` maps to a dedicated newtype, not a primitive alias, so the compiler catches accidentally mixing fixed-point and plain-`i32` arithmetic (impossible in the original C). `transpiler/src/codegen/runtime/fixed.rs` (`FixedT`) mirrors `m_fixed.c` exactly rather than reimplementing "cleaner" semantics -- `fixed_mul` widens to `i64` before shifting (avoiding the intermediate overflow a 32-bit multiply would hit) then truncates back; `fixed_div` saturates to `i32::MIN`/`MAX` via the original's own cheap pre-check rather than detecting overflow after the fact; `fixed_div2` goes through `f64`, matching the original's actually-compiled path (its `long long`-only alternative is `#if 0`'d out in the source itself) and panics past 32-bit range carrying the original's own (slightly misleading -- it's an overflow, not a literal zero divisor) message. Plain `+`/`-`/unary `-` wrap on overflow rather than panic, matching C `int`'s two's-complement behavior in practice rather than Rust's debug-mode default -- needed since `docs/03_TRANSPILER.md`'s own validation strategy is behavior-identical output, not "morally equivalent" output.
- **Enums** -- **Decided and implemented**: plain integer constants (`pub const S_PLAYER: i32 = 5;` or similar), not real Rust `enum`s with `#[repr(i32)]`. Doom's state/animation system does arithmetic directly on enum values (`state + 1`-style sequencing), which a real Rust enum has no direct equivalent for without a conversion shim at every such site. `transpiler/src/codegen/enum_values.rs` (`compute_enum_values`, `render_enum_consts`) computes each variant's actual value from its AST (implicit `previous + 1` sequencing, or a literal-only constant fold for an explicit value) and renders it. Measured first (`examples/enum_value_survey.rs`), matching this project's usual practice before building an evaluator: of the corpus's 1642 enum variants across 43 defining specs, 1592 are implicit and 50 have an explicit value built purely from integer literals (bare, unary-negated, or combined with `+`/`*`, however deeply nested) -- 1638 of 1642 (99.76%) fold cleanly. The remaining 4 (`doomdef.h`'s `INVULNTICS`/`INVISTICS`/`INFRATICS`/`IRONTICS`, all `N * TICRATE`) reference a `#define`d macro rather than a literal; left unresolved rather than pulling in full macro substitution for four variants, matching `visibility.rs`'s own "not worth more machinery for a two-symbol gap" precedent. Not yet done: deciding which Rust module each constant's block of `pub const`s actually renders into (an analogous "owner" question to `source_symbol_imports`, not yet built for this namespace).
- **Structs** -- **All 9 real thinker subclasses fully translated**, including `mobj_t`: `transpiler/src/codegen/struct_fields.rs` (`map_struct_fields`, `render_struct`) translates a C struct's field list to Rust, field by field, failing loudly on anything it doesn't recognize rather than guessing. `slidedoor_t` (`p_spec.h`) is `#if 0`'d out dead code in the corpus itself (confirmed by direct read), so the real count is 9 -- `fireflicker_t`/`lightflash_t`/`strobe_t`/`glow_t`/`plat_t`/`vldoor_t`/`ceiling_t`/`floormove_t`/`mobj_t` -- not the 10 the Memory Model section originally estimated.
  - **Type mapping decided so far** (each field type maps to exactly one of these, chosen for the reason noted): the embedded `thinker_t thinker;` header is dropped entirely (the `enum Thinker` wrapper + `Handle<Thinker>` replace its role) · `fixed_t` -> `FixedT` · `boolean` -> Rust's native `bool`, not `i32` (Doom never does arithmetic on *this* enum the way it does the animation-sequence ones, so the Enums decision doesn't apply to it) · any locally `typedef enum`'d name -> `i32`, resolved generically via `collect_enum_typedef_names` rather than hardcoded per enum · `int`/`short`/`angle_t` (`typedef unsigned`, `tables.h`) -> `i32`/`i16`/`u32` · `sector_t*`/`struct subsector_s*` -> `SectorId`/`SubsectorId` (`runtime/geometry.rs`; level geometry is bulk-allocated once per level and never individually freed, so a plain index needs no generation counter -- corpus-checked non-`Option` for both) · self-referential `struct mobj_s*` (`snext`/`sprev`/`bnext`/`bprev`/`target`/`tracer`) -> `Option<Handle<Thinker>>` (genuinely nullable: list-end sentinels, "no target yet") · `mobjinfo_t*`/`state_t*` -> `&'static MobjInfo`/`&'static State` (`mobjinfo[]`/`states[]` in `info.h` are static, program-lifetime, read-only tables that never get freed or replaced, so a real reference is simpler than another index -- the tables themselves aren't translated yet, a separate, large undertaking) · `struct player_s*` -> `Option<PlayerId>` (`runtime/player.rs`; `player_t players[MAXPLAYERS]` in `g_game.c` is a plain fixed-size array, program lifetime not per-level, same reasoning as `SectorId` -- no separate arena needed) · `mapthing_t` (embedded by value, e.g. `mobj_t.spawnpoint`) -> `MapThing`, itself just five `short` fields.
  - **Two Rust-keyword-collision bugs found and fixed** (both caught by tests asserting actual rendered/mapped output, not by inspection): `boolean`'s own `false`/`true` enum constants don't parse and aren't escapable (fixed in `enum_values.rs` -- they're literal tokens, not identifier-class keywords, so the whole enum's constants are simply skipped, which is moot anyway once `boolean` maps to `bool`); and several structs have a field literally named `type` (`pub type: i32,` doesn't parse either), which *is* escapable via `r#type` (a genuine identifier-class keyword) -- `rust_field_name` applies that generically, failing loudly only for the four keywords raw-identifier syntax truly can't escape (`crate`/`self`/`super`/`Self`) plus `true`/`false`.
  - **Parsing headers for their own struct definitions** needed the rough, typedef-table-free scan (`extract_top_level_decls`), not `parse_full`: several of these headers can't parse standalone (e.g. `p_spec.h`'s `extern boolean levelTimer;` needs `boolean` typedef'd by whichever `.c` file includes it first), and even parsing a `.c` file that includes one doesn't splice the header's own struct *definitions* into that file's `TranslationUnit.items` (`parse_full`'s header handling only seeds typedef names, the same as Step 6b's import model).
  - `info: mobjinfo_t*` is observably redundant with `mobj_t.type` corpus-wide (always `&mobjinfo[type]`, per `p_mobj.c`/`p_saveg.c`), but is kept as its own field -- preserving the original's struct shape 1:1 rather than silently restructuring it away.

- **Level geometry (`r_defs.h`) -- all core structs fully translated**: `vertex_t`, `degenmobj_t`, `side_t`, `subsector_t`, `seg_t`, `line_t` (`struct line_s`), `sector_t`, and `node_t` all map completely. New pieces this needed:
  - **Array support, any dimension**: a C array field (`int blockbox[4];`) maps to a Rust array (`[i32; 4]`), reusing `enum_values.rs`'s own `fold_const_int` for the length rather than a new evaluator -- every array length in the corpus fields mapped so far is a bare integer literal, the exact shape that folder already handles. Nested arrays (`node_t`'s `fixed_t bbox[2][4]`) work too (`wrap_arrays`), but needed the dimension order checked directly against the parser's real AST output rather than assumed: `a[2][4]`'s declarator nests as `Array(Array(Ident(a), 2), 4)`, with the *outermost* AST node holding the *last*-written bracket -- which is C's fastest-varying, innermost dimension (`a[2][4]` is "2 rows of 4", i.e. `[[T;4];2]` in Rust, not `[[T;2];4]`). Getting this backwards would have silently transposed every 2D array; a dedicated test locks the correct order in directly, not just incidentally via `node_t`.
  - **`VertexId`/`SideId`/`LineId`** (`runtime/geometry.rs`) join `SectorId`/`SubsectorId`, same "bulk-allocated once per level, never individually freed, no generation counter" reasoning. A cross-referencing type is sometimes spelled two ways in the corpus for the same underlying type -- `line_t*` (typedef form, e.g. `seg_t.linedef`) vs. `struct line_s*` (tag form, e.g. inside `line_t`'s own neighboring fields) -- both map to `LineId`; same pattern already established for `mobj_t`/`struct mobj_s`.
  - **Three name-based (not type-based) special cases, all corpus-verified before adding**: `specialdata: void*` (`sector_t`/`line_t`) always holds a `ceiling_t*`/`plat_t*`/`vldoor_t*`/`floormove_t*` back-reference (checked for truthiness before starting a new mover, reset to `NULL` when done -- `p_ceilng.c`/`p_plats.c`/`p_floor.c`) -> `Option<Handle<Thinker>>`. `backsector: sector_t*` (`line_t`/`seg_t`) is genuinely nullable for one-sided lines -- `if (!ld->backsector)`/`if (!backsector)` (`p_map.c`, `r_bsp.c`, `p_maputl.c`) -- unlike its sibling `frontsector`, dereferenced with no guard anywhere in the corpus, so only `backsector` gets `Option<SectorId>`. `lines: struct line_s** lines;` (`sector_t`) is a *dynamically*-sized array (`// [linecount] size` in the header itself -- a pointer to a heap-allocated array of pointers, sized by the sibling `linecount` field, not by any fixed declarator dimension) -> `Vec<LineId>`, the standard translation for that C idiom; `linecount` itself stays its own field regardless, redundant with `lines.len()` once `lines` is a real `Vec` -- same "preserve the original's struct shape 1:1" call already made for `mobj_t.info`'s redundancy with `.type`. All three are scoped to their specific field name, not to `void*`/`sector_t*`/`T**` in general, since a blanket type-only rule would be wrong for some other field this step hasn't individually checked.
  - **A real bug caught before shipping**: `backsector` was initially mapped as a bare `SectorId`, matching every other `sector_t*` field mapped so far -- the corpus check (done *because* this project checks nullability before deciding `Option` vs. bare, not after) surfaced the `frontsector`/`backsector` asymmetry, fixed in the same commit rather than shipped and found later.

- **The `Thinker` enum -- implemented, shape only**: `transpiler/src/codegen/thinkers.rs` renders `pub enum Thinker { FireFlicker(FireFlicker), ..., Mobj(Mobj) }` wrapping all 9 translated structs, plus a stub `match` dispatch (one arm per variant, `todo!()` body) replacing the original's hand-rolled C vtable (`thinker_t.function`, called as a function pointer). **Deliberately not real dispatch logic**: every Phase 3 step so far -- module graph, `use` blocks, enum constants, struct fields, this enum -- has been data *shape*, never function-body logic. Translating an actual tick function (e.g. `T_FireFlicker`'s random-timer logic) needs C-statement/expression-to-Rust transpilation, which nothing in this codebase does yet -- a large, separate undertaking, deliberately not started here; guessing the dispatch's real signature (what context a tick needs -- world state, the arena itself, ...) before any real body exists to check it against would just mean redoing it later. Variant names (`FireFlicker`, `VerticalDoor` for `vldoor_t` matching the original's own `T_VerticalDoor` rather than the struct's more cryptic name, ...) are picked explicitly per struct -- no automatic snake_case_t -> PascalCase converter exists, and wouldn't even help for a name like `fireflicker_t` (no underscore to split on).

Not yet done: real tick-function bodies (blocked on C-statement/expression transpilation, not started at all); translating `info.c`'s static `mobjinfo[]`/`states[]` tables (a separate, large undertaking); rendering struct/enum output into an actual module file (`use_stmt.rs`/`mod_tree.rs` output, not yet connected to struct rendering); every other struct in the corpus beyond thinkers and this core geometry cluster (e.g. `r_defs.h`'s own `drawseg_t`/`vissprite_t`/`visplane_t`/... further down the same file).
- **Doom Action Pointers**:
  - Map function pointers to Rust function pointers (`fn(...)`) or enum-based dispatch tables. Not yet designed.
- **Module Structure (`.c`/`.h` -> Rust module)**:
  - Each `.c`/`.h` pair (e.g. `p_map.c` + `p_map.h`) merges into one Rust module. Items declared in the `.h` become `pub`; items that only exist in the `.c` stay private. This mirrors Rust's own visibility model and the original C author's intent -- the header already *is* their declaration of "here's my public API."
  - **Headers with no matching `.c`** (pure declaration headers: shared typedefs/structs/macros, no implementation) become their own module, with everything `pub`. Confirmed via corpus scan: 13 such headers exist -- `doomtype.h`, `doomdata.h`, `d_player.h`, `d_think.h`, `d_ticcmd.h`, `d_event.h`, `d_textur.h`, `d_englsh.h`, `d_french.h`, `p_local.h`, `r_defs.h`, `r_local.h`, `r_state.h`. **Implemented**: `transpiler/src/codegen/modules.rs` (`build_module_graph`) enumerates all 75 modules (62 Source, one per `.c` file, plus these 13 HeaderOnly) and, for every Source module, which of the 13 it needs a `pub use header_only_module::*;` from -- following its own `#include` graph *transitively*, the same closure `ExportResolver`/`DeclaredTypesResolver`/`ImportResolver` already walk for their own purposes, reused here rather than reimplemented. 55 of the 62 Source modules need at least one; `doomtype` alone is needed by 53. A glob is safe here because everything a header-only header declares really is defined in that Rust module -- one line regardless of how much it covers, so "declared, not used" (mirroring C's own `#include` semantics) costs nothing.
  - **Implemented -- `.c`-to-`.c` exact-path imports**: a header (of either kind) can `extern`-declare a function/global actually *defined* in a different `.c` file -- `p_local.h` declares `P_TryMove`, but the item lives in the `p_map` module, not `p_local`'s, so no glob of `p_local` would ever surface it. `build_module_graph`'s `source_symbol_imports` resolves these to an exact `use owner::name;` per symbol, built from two existing pieces: `resolve_module_visibility`'s public sets, unioned corpus-wide into a `name -> defining module` map (unique per C's one-definition rule for external linkage); and `typecheck::resolve`'s Step 1 symbol resolver, run *unseeded* per file, whose `unresolved` identifiers are exactly the ones that trace to some other module. This tier is deliberately *usage-pruned*, unlike the header-only glob: measured against the corpus, "declared, not used" here would have meant `p_map.c` (player movement) picking up exact-path imports for symbols from `r_main`/`r_draw` (rendering) it never calls -- 13,709 exact-path imports corpus-wide, ~249 per importing module on average, mostly dead. Pruned to actual references: 1206 total, 442 module-pair edges, 50 of 62 Source modules need at least one. The one pattern the resolver can't distinguish -- `RawDeclarationIndex`'s bare top-level redeclaration with no header at all (e.g. `m_misc.c`'s own `extern int key_right;`) -- is resolved locally by the file's own redeclaration and would never show up unresolved even when used, so its mere existence is treated as need instead; narrow enough (2 corpus-wide symbols) not to chase further.
  - **Implemented -- rendering the `use` block**: `transpiler/src/codegen/use_stmt.rs` (`render_use_block`) turns the two import maps above into the actual Rust text a module's own file needs at its top: one `pub use crate::header_only::*;` line per header-only import (sorted), then one grouped `use crate::owner::{a, b, ...};` line per exact-path owner (owners and the names within each line both sorted, since the underlying maps are hash-based and iterate in unspecified order -- generated source needs to be deterministic regardless). Exact-path lines are deliberately plain `use`, not `pub use`: they're a module's own internal calls into another's public API, not something it means to re-export. `p_map`'s real rendered block, for example, globs in its 10 needed header-only modules and pulls precise symbol lists from 15 different Source modules (`p_maputl`, `p_mobj`, `r_main`, ...), nothing from unrelated subsystems like `r_draw`.
  - **Implemented -- the crate module tree**: `transpiler/src/codegen/mod_tree.rs` (`render_mod_declarations`) renders the other half of the boilerplate `use_stmt.rs` doesn't cover -- a `pub mod name;` line for every one of the 75 modules, sorted. `pub`, not private: `use_stmt.rs`'s own output reaches every module by a `crate::name::...` path, which needs the module itself publicly reachable from the crate root regardless of what `resolve_module_visibility` decided about its individual items.
  - **Implemented -- true `extern` linkage vs. "declared in the matching header"**: "declared in this file's own `.h` => `pub`, else private" is a heuristic that follows C *convention*, not C's actual linkage rules. Measured with `transpiler/examples/extern_linkage_survey.rs` (see `docs/KNOWN_LIMITATIONS.md`): of 1360 externally-linked definitions corpus-wide, only 25% were both declared in their own matching header *and* genuinely visible to other files only through it. `transpiler/src/codegen/visibility.rs` (`resolve_module_visibility`) replaces it with four combined signals: (1) declared by any header reachable through the defining `.c` file's own `#include` graph (`ExportResolver::resolve_via_includes`, not just the name-matching header -- covers `doomstat.h`-style centralization and the 13 no-matching-header `.c` files, whose symbols attach to whichever shared header they actually include, e.g. `p_local.h`); (2) declared in the file's own matching header even when that file never `#include`s it itself (`r_bsp.c` never includes `r_bsp.h`, yet `r_bsp.h`'s declarations are still real); (3) redeclared as a bare prototype/`extern` directly at another `.c` file's own top level, bypassing headers on both ends (`RawDeclarationIndex`); private otherwise. Cross-checked against the survey's independent "used elsewhere" ground truth: 2 of 1360 definitions remain wrongly private (`rndindex`, `skyflatnum` -- both declared only in `doomstat.h`, which their defining files have no `#include` relationship to at all), left undone as not worth more machinery for a two-symbol gap.

## 🔷 Target 2: .NET / C# Transpiler

### 1. Architectural Choices
- Generate C# structs / classes.
- Use `unsafe` blocks for low-level memory and buffer manipulation if required, or translate to safe managed arrays / `Span<T>`.

## 🧪 Validation & Execution Strategy
1. **Compilation Validation**: Ensure generated Rust code compiles cleanly via `cargo check` and `cargo build`.
2. **Deterministic Output Comparison**: Compare game tick execution and fixed-point math against native Doom to verify behavior equivalence.
